# Фича: идентификация спикеров по голосу (именованные голоса)

Проработка требований и UX для FR-8 (Фаза 3). Это **проект для обсуждения**, не финал.
Код пока не пишем — сначала фиксируем, что именно и как должно работать.

---

## 0. Главное, что надо понять до всего остального

Сейчас у нас **диаризация**, а не **узнавание голоса**. Это разные задачи, и фича — про вторую.

| | Диаризация (есть) | Идентификация (хотим) |
|---|---|---|
| Что делает | в *одном файле* разделяет голоса: «Спикер 1/2/3» | подставляет **имя** конкретного человека |
| Память | нет, метки локальны для файла | постоянная база «отпечатков» голоса |
| «Спикер 1» в файле A и в файле B | **разные люди** (совпадение случайно) | один и тот же человек = одно имя везде |
| Технически | кластеризация (pyannote) | эмбеддинг голоса + сравнение с базой (cosine) |

Вывод: это **новая подсистема**, а не галочка в настройках. Нужны: хранилище голосовых
отпечатков, извлечение эмбеддинга на каждый кластер, матчинг с базой, и — критично —
UI, где ты слушаешь и присваиваешь имена. Объём — сопоставимо с Фазой 2, не меньше.

## 1. Честный ответ на вопрос «насколько это вообще реально с iPhone-микрофоном»

Коротко: **реально и полезно, но это «подсказка», а не «истина». Не Plaud-магия.**

**Микрофон iPhone — не узкое место.** Он хороший. Ограничение в другом: запись **одноканальная**,
поэтому система не может разделять людей «по направлению» (как массив микрофонов в зале).
Всё держится на различии самих голосов и на акустике.

**Где работает хорошо (реалистично 85–95% реплик названы верно):**
- твой собственный голос (его проще всего узнавать — много чистых примеров);
- 2–4 явно разных голоса, разговор 1-на-1 или маленькая встреча;
- говорящие близко к телефону, тихая комната, мало перебивок;
- у каждого набирается хотя бы ~20–30 секунд речи суммарно.

**Где деградирует (вплоть до бесполезности):**
- **дальнее поле**: телефон на столе, 5 человек, эхо/реверберация — здесь и сама диаризация
  ошибается, а идентификация поверх неё умножает ошибки;
- **перекрытие речи**: говорят одновременно → эмбеддинг «загрязняется» → неверное имя;
- **короткие реплики** («ага», «да», «угу») — сигнала слишком мало, голос не узнать;
- **похожие голоса**: один пол, близкий тембр/акцент → путаница;
- **смена обстановки**: записал «эталон» в тишине, узнаёшь в машине/на улице → отпечаток «плывёт»;
- фоновая музыка/телевизор/громкий шум.

**Фундаментальный компромисс порога (от него не уйти):**
- порог строгий → твой голос иногда подпишется как «Спикер 2» (ложный отказ);
- порог мягкий → чужой человек подпишется твоими инициалами (ложное срабатывание).

Поэтому дизайн обязан этот компромисс **уважать**, а не прятать:
1. метки «Спикер N» от диаризации остаются базой **всегда**;
2. имя — это **наложение поверх**, только когда уверенность выше порога;
3. неуверенный голос честно остаётся «Спикер N (?)», а не угадывается;
4. есть **цикл исправления**: ты поправил ошибку — система до-обучила отпечаток. Это
   главный рычаг качества: чем больше подтверждённых примеров, тем точнее дальше.

> Реалистичная планка для v1: «для меня и 2–3 постоянных собеседников в нормальных условиях —
> отлично; в шумной переговорке на 6 человек — подсказка, которую надо проверять».

## 2. Концепция

```
        ЗАПИСЬ ОДИН РАЗ (enrollment)                  КАЖДЫЙ НОВЫЙ ФАЙЛ
   ┌──────────────────────────────┐         ┌────────────────────────────────┐
   │ кластер «Спикер 1» в файле    │         │ диаризация → кластеры + эмбеддинг│
   │  → ты говоришь «это MS»       │         │ на каждый кластер               │
   │  → эмбеддинг кластера         │         │      │                          │
   │    сохраняется в базе под MS  │         │      ▼ cosine vs база голосов   │
   └──────────────┬───────────────┘         │  лучший матч > порога? → имя    │
                  │                          │  иначе → «Спикер N»             │
                  ▼                          └────────────────────────────────┘
        ┌───────────────────┐                          │
        │ База голосов       │◄─────── цикл исправления ┘
        │ имя → [эмбеддинги] │   (поправил/подтвердил → отпечаток улучшился)
        └───────────────────┘
```

## 3. Функциональные требования (раскрытие FR-8)

### FR-8.1. База голосовых отпечатков (gallery)
- Локальная база известных голосов: **имя/инициалы → один или несколько эмбеддингов**.
- Несколько эмбеддингов на голос (а не один усреднённый) — для устойчивости к разным условиям.
- Хранится **только локально** на Mac (биометрия — не в iCloud, не в Telegram). См. §7.

### FR-8.2. Извлечение эмбеддингов при обработке
- При включённой идентификации worker получает на каждый кластер диаризации **эмбеддинг голоса**.
- Источник — pyannote: пайплайн `speaker-diarization-3.1` умеет отдавать эмбеддинги кластеров
  (`return_embeddings=True`). Отдельную модель тащить не нужно. *(проверить API на нашей версии)*

### FR-8.3. Матчинг с базой
- Для каждого кластера: cosine-сходство с центроидами голосов в базе.
- Лучший матч **выше порога** → подставляется имя; иначе кластер остаётся «Спикер N».
- Порог настраивается. В UI — пресеты «строго / сбалансировано / мягко», а не сырые числа.
- Если два кластера в одном файле претендуют на одно имя — имя получает более уверенный,
  второй остаётся «Спикер N» (один человек не может быть в двух местах одновременно).

### FR-8.4. Enrollment (как голос попадает в базу) — основной путь «из файла»
- После обработки файла пользователь в окне **«Разобрать спикеров»** видит найденные кластеры,
  у каждого — кнопка прослушать образец и поле «кто это».
- Присвоил имя → эмбеддинг(ы) этого кластера сохраняются под этим именем (новым или существующим).
- Это переиспользует уже имеющиеся данные, отдельная «студийная» запись не нужна.

### FR-8.5. Enrollment — дополнительный путь «эталонная запись» *(опционально, можно во v2)*
- Можно скормить чистую запись одного человека (≈30 c) и сразу назначить имя.
- Выше качество, но больше трения и редко есть чистые сэмплы чужих людей. Не приоритет.

### FR-8.6. Цикл исправления (active learning)
- В окне «Разобрать спикеров» пользователь может **исправить** неверно подставленное имя
  или **подтвердить** верное.
- Исправление/подтверждение **дописывает** эмбеддинг кластера в галерею этого человека →
  отпечаток со временем улучшается. Это ключевой механизм роста точности.
- Ошибочно добавленный пример можно удалить (см. FR-8.7).

### FR-8.7. Управление голосами
- Окно «Голоса»: список известных людей (имя, число образцов, дата).
- Действия: переименовать, удалить голос, удалить отдельный образец, объединить два голоса
  (если случайно завёл одного человека дважды).

### FR-8.8. Поведение по умолчанию и обратная совместимость
- Идентификация — **опция поверх** диаризации (диаризация должна быть включена).
- Выключена по умолчанию; пустая база = поведение как сейчас («Спикер N» везде).
- Неизвестный голос **никогда не угадывается силой** — остаётся «Спикер N».

## 4. UX-потоки

### 4.1. Где живёт UI «разобрать спикеров»

Проблема: menu-bar приложение **не имеет окна просмотра транскрипта**. Тегирование требует
послушать и присвоить → нужно новое окно. Предлагаю минимальное **«Разобрать спикеров»**,
открывается:
- из меню: пункт «Разобрать спикеров последнего файла…»;
- из системного уведомления/Telegram: «обработано, 2 неизвестных голоса — разобрать?».

```
┌──────────────────────────────────────────────────────────────┐
│  Разобрать спикеров — «New Recording 20» (28.06 14:01)         │
├──────────────────────────────────────────────────────────────┤
│  ▶  Спикер 1   ████░░ 0:42 речи     [ MS ▼ ]   уверенность —   │
│        «Так, это проверка того, как работает…»                 │
│                                                                │
│  ▶  Спикер 2   ██░░░░ 0:11 речи     [ ? выбрать ▼ ]            │
│        «угу, да, понятно»                                       │
│                                                                │
│  ▶  Спикер 3   █████░ 1:20 речи     [ Ася ✓ ]  совпало 0.71    │
│        «давайте по второму пункту…»                            │
├──────────────────────────────────────────────────────────────┤
│  [ Применить имена и пересохранить транскрипт ]    [ Закрыть ] │
└──────────────────────────────────────────────────────────────┘
```
- `▶` — проиграть характерный фрагмент этого кластера (worker заранее вырезал образец).
- Выпадашка `[ … ▼ ]`: выбрать существующий голос / создать новый / оставить «Спикер N».
- Где система сама подставила имя — показывает совпадение (0.71) и галочку для подтверждения.
- «Применить» → перезаписывает `.txt`/`.srt` с именами и до-обучает базу. Опционально —
  перешлёт обновлённый файл в Telegram.

### 4.2. Поток первого знакомства (твой сценарий)
1. Записал и обработал файл → пришёл транскрипт со «Спикер 1/2».
2. Открыл «Разобрать спикеров» → нажал ▶ на «Спикер 1», узнал свой голос → выбрал «новый: MS».
3. Применил → транскрипт переписался с «MS», голос MS попал в базу.
4. В следующих файлах твой голос **сразу** подписывается «MS» (если уверенность выше порога).

### 4.3. Поток узнавания в новых файлах
- Идентификация включена, база не пуста.
- Worker подставляет имена там, где уверен; остальное — «Спикер N».
- В транскрипте у автоподставленных имён может быть пометка неуверенности (см. §5).
- Если в файле остались неизвестные голоса — уведомление предлагает «разобрать».

### 4.4. Управление голосами
```
┌─────────────────────────────────────────────┐
│  Голоса                                       │
├─────────────────────────────────────────────┤
│  MS    (я)        12 образцов   создан 28.06  │  [Переименовать][Удалить]
│  Ася              4 образца     создан 28.06  │  [Переименовать][Удалить]
│  Партнёр Б        2 образца     создан 27.06  │  [Объединить…]
├─────────────────────────────────────────────┤
│  Порог узнавания:  ( ) строго (•) баланс ( ) мягко │
└─────────────────────────────────────────────┘
```

## 5. Формат вывода с именами

- Имя вместо «Спикер N»:
  `[00:00:01] MS: Так, это проверка того, как работает моя система…`
- Неуверенное автоузнавание — честная пометка, чтобы не вводить в заблуждение:
  `[00:01:10] Ася(?): давайте по второму пункту…`  ← знак вопроса = ниже «уверенного» порога
- Неизвестный голос — как сейчас: `[00:00:42] Спикер 2: …`
- В `.srt` — то же правило префикса (как сейчас в `output.py: _with_speaker`).

## 6. Данные и хранение (черновик, к этапу архитектуры)

- Каталог: `~/ASR/voices/` (локально, **не** iCloud).
  - `index.json` — `{ "MS": {"created":…, "samples":[ids…]}, … }`.
  - `embeddings/<id>.npy` — отдельные векторы образцов (или один `.npz` на голос).
- Матчинг: центроид голоса = среднее его эмбеддингов; cosine; порог по пресету.
- Образцы аудио для прослушивания в окне: короткие срезы рядом с транскриптом
  (например `~/ASR/ASROutput/.../<base>.speakers/spk1.m4a`), чистятся по ретенции.
- Без БД: JSON + npy достаточно для одного пользователя и десятков голосов (NFR-7).

## 7. Приватность и этика (важно, нельзя замолчать)

- Голосовой отпечаток — **биометрия**. Хранение отпечатков других людей без их ведома имеет
  этическую и, возможно, юридическую сторону — особенно для записей встреч.
- Дизайн: всё **локально**, только у владельца, ничего не уходит в iCloud/Telegram/сеть.
- Ответственность за enrollment чужих голосов — на пользователе; в onboarding/доке — явная оговорка.
- Удаление голоса должно быть полным (вектора + образцы аудио).

## 8. Предлагаемое разбиение (чтобы не утонуть)

- **v1 (минимум полезного):**
  - извлечение эмбеддингов кластеров (FR-8.2);
  - база голосов + матчинг + порог-пресеты (FR-8.1, 8.3);
  - окно «Разобрать спикеров»: enrollment из файла + исправление + до-обучение (FR-8.4, 8.6);
  - вывод с именами и пометкой неуверенности (§5);
  - локальное хранилище (§6), приватность (§7).
- **v2 (позже):** окно «Голоса» (FR-8.7) в полном виде, эталонная запись (FR-8.5),
  объединение голосов, авто-пере-доставка в Telegram, тонкая настройка порога по человеку.

   + пометка + возможность поправить.
3. **Что делать при исправлении** — только дописывать пример в базу, или ещё и автоматически
