# Архитектура

## 1. Обзор

Полностью локальная система без серверов. Три «места»: iPhone (захват), iCloud Drive (транзитная
труба), Mac (обработка, хранение, доставка). Облачной транскрипции нет. Аудио и транскрипты хранятся
**локально на Mac**; iCloud используется только для кратковременной передачи файла. На Mac работает
**приложение в строке меню** (.dmg), которое заменяет launchd-сторож и оркестрирует обработку
(UX/UI — см. [ux-ui.md](ux-ui.md)).

```
┌─ iPhone 14 Pro ───────────────┐
│ Voice Memos: запись            │   (фон, заблокированный экран, любая длительность)
│   → «Поделиться»               │
│   → Shortcut «MLaud» (опц.)     │   маршрутизация в папку; можно и вручную «Сохранить в Файлы»
│       сохранить файл в iCloud   │   имя: YYYY-MM-DD_HH-MM-SS.m4a
└───────────────┬───────────────┘
                ▼
┌─ iCloud Drive (ТРАНЗИТ) ─────────────┐
│  ASR/ASRInbox/AllRecords/  ← новые     │   синхронизируется Apple-ом iPhone↔Mac
└───────────────┬───────────────────────┘
                │ появился/докачался файл
                ▼
┌─ Mac (M5, 48 ГБ) ─────────────────────────────────────────────────┐
│  Menu bar app (всегда жив, лёгкий, RAM ≈ 0, БЕЗ модели)            │
│    • FSEvents watch на ASRInbox/AllRecords                         │
│    • подписка на NSWorkspaceDidWake (пробуждение → sweep)          │
│    • таймер-страховка (sweep раз в 1-2 мин)                        │
│        │ есть новые файлы → spawn                                   │
│        ▼                                                            │
│  worker (эфемерный подпроцесс)                                     │
│    1. взять lock (исключить параллельный запуск)                   │
│    2. убедиться, что файлы реально скачаны (не .icloud)            │
│    3. СКОПИРОВАТЬ аудио на локальный диск, УДАЛИТЬ из iCloud inbox  │
│    4. ЗАГРУЗИТЬ модель GigaAM-v3 (MLX) ← RAM занялась               │
│    5. цикл: транскрибировать каждый файл (текст + тайм-коды)        │
│       [Фаза 2: диаризация pyannote → метки спикеров]               │
│       [Фаза 3: сопоставление голосов с базой → имена]             │
│       [хук: авто-суммаризация — позже]                            │
│    6. сохранить .txt/.srt/.json в ~/ASR/ASROutput/AllOutputs/<дата>│
│    7. отправить .txt файлом в Telegram                            │
│    8. переместить аудио в ~/ASR/Processed/AllRecords/<дата>        │
│    9. exit ← RAM освободилась                                      │
│                                                                    │
│  Локальное хранилище (НЕ iCloud):                                  │
│    ~/ASR/Processed/AllRecords/<дата>/...m4a   ← аудио              │
│    ~/ASR/ASROutput/AllOutputs/<дата>/...txt   ← транскрипты        │
│    ~/ASR/service/                             ← логи, состояние, lock│
└───────────────┬───────────────────────────────────────────────────┘
                │ .txt файл / ошибка → уведомление (Telegram + системное)
                ▼
        ┌─ Telegram-бот ─┐
        │  файл тебе      │
        └────────────────┘
```

## 2. Компоненты

### 2.1. iPhone — захват (Shortcut опционален)
- **Контракт системы — папка** `ASRInbox/AllRecords`, а не Shortcut. Приложение реагирует на
  появление файла независимо от способа его добавления.
- **С Shortcut (рекомендуется):** share-target принимает аудио из «Поделиться» в Voice Memos →
  кладёт в папку с авто-именем `YYYY-MM-DD_HH-MM-SS.m4a`. Удобно, без ручной навигации.
- **Без Shortcut:** «Поделиться → Сохранить в Файлы → выбрать папку» вручную. Работает, но больше
  трения. Можно начать так и добавить Shortcut позже.
- Заголовок не запрашивается; имя — по дате/времени. Один режим на всё (ADR-007).

### 2.2. iCloud Drive — транзитная труба
- Папка `ASR/ASRInbox/AllRecords/` — единственное, что в iCloud. **Постоянного хранения нет.**
- Роль: развязать «момент записи» и «момент обработки», не требуя своего сервера и не заставляя
  Mac быть онлайн при записи.
- worker после приёма **удаляет** файл из inbox, поэтому iCloud не забивается (NFR-6).

### 2.3. Mac — приложение в строке меню (всегда живо)
- **Нативное menu bar приложение** (.dmg), заменяет launchd-сторож. Подробности UX — [ux-ui.md](ux-ui.md).
- Следит за inbox через **FSEvents**, подписано на **пробуждение из сна** (`NSWorkspaceDidWake`),
  плюс **периодический sweep** (1-2 мин) — страховка от пропущенных событий и поздней iCloud-докачки.
- Память близко к нулю: приложение **не держит модель**, только ждёт событий и спавнит worker.
- Показывает статус (иконка + меню), последние результаты, системные уведомления; имеет окно
  настроек (папки, Telegram, модель, автозапуск).

### 2.4. Mac — worker (эфемерный)
- Запускается, делает работу, **завершается** → освобождает RAM (NFR-2).
- **Батчинг обязателен:** модель грузится один раз за прогон. При 50-330x realtime доминирует
  именно загрузка модели, поэтому поштучный запуск расточителен.
- Лок-файл защищает от параллельных запусков (NFR-4).
- Порядок: приём → транскрипция → [диаризация] → [имена] → сохранение → Telegram → архивация аудио.

### 2.5. Движок транскрипции — GigaAM-v3 (MLX)
- Пакет: `gigaam-mlx` (нативный MLX, без PyTorch). Целевой вариант — `rnnt` (точность).
- Тайм-коды: SRT (посегментные) из коробки; пословные — из официального `gigaam` (torch) при
  необходимости (OQ-5).
- Фолбэк движка: официальный `gigaam` (torch) — для пословных тайм-кодов и длинных файлов с VAD.
- RU/EN-смешанная речь поддерживается.

### 2.6. Диаризация — pyannote (Фаза 2)
- `pyannote/speaker-diarization-3.1` (PyTorch, HF-токен для скачивания весов; инференс локальный).
- Пайплайн: pyannote даёт сегменты «кто-когда» → мёрджим с тайм-кодами GigaAM → транскрипт с
  метками «Спикер N».
- **Важно:** это возвращает зависимость от PyTorch рядом с MLX. Оба стека локальные, эфемерные.
- Альтернатива — облегчённый «гибрид» (VAD + эмбеддинги + кластеризация), если pyannote тяжёл/неточен.

### 2.7. Идентификация по голосу — enrollment (Фаза 3)
- База голосовых эмбеддингов известных людей + заданные пользователем имена/пометки.
- При обработке: эмбеддинг каждого кластера сравнивается с базой → проставляется реальное имя;
  неизвестные остаются «Спикер N» с возможностью доучивания.

### 2.8. Доставка — Telegram-бот
- Бот создаётся через @BotFather; токен и `chat_id` — в `.env`.
- Отправка через Bot API `sendDocument` (всегда файлом). Ошибки — туда же.

## 3. Поток данных (happy path, MVP)

1. Пользователь пишет встречу в Voice Memos → «Поделиться» → Shortcut «MLaud» (или вручную в папку).
2. Файл `2026-06-21_14-30-05.m4a` попадает в `iCloud/ASR/ASRInbox/AllRecords/`.
3. iCloud синхронизирует файл на Mac (когда Mac онлайн).
4. Menu bar приложение видит новый файл (FSEvents / sweep / после пробуждения) → спавнит worker.
5. worker берёт lock, проверяет, что файл скачан, копирует на локальный диск, удаляет из iCloud.
6. Грузит модель, транскрибирует → текст + тайм-коды.
7. Сохраняет `~/ASR/ASROutput/AllOutputs/2026-06-21/14-30-05.txt` (+ `.srt`/`.json`).
8. Шлёт `.txt` файлом в Telegram; показывает системное уведомление.
9. Перемещает аудио в `~/ASR/Processed/AllRecords/2026-06-21/`.
10. Завершается, освобождает память. Приложение обновляет иконку/меню «Готово».

## 4. Состояние и идемпотентность

- Состояние пайплайна выражено расположением файлов: `iCloud/ASRInbox/AllRecords` (ждёт приёма) →
  `~/ASR/Processed/AllRecords` (готово). Источник истины — файловая система, без БД.
- worker обрабатывает только то, что в `inbox`; принятое копирует локально и удаляет из `inbox`.
- Падение **до** удаления из iCloud → файл остаётся в `inbox`, будет повторно принят (приемлемо:
  максимум повторная отправка в Telegram; данные не теряются).
- Лок-файл предотвращает гонку двух worker'ов.

## 5. Edge-cases и риски

- **iCloud переполнен (NFR-6).** Если места нет, даже транзитный файл может не синкнуться. Митигация:
  немедленное удаление из `inbox` после приёма; мониторинг свободного места; при проблемах —
  рассмотреть альтернативный транспорт (см. п. 8).
- **iCloud-плейсхолдеры (`.icloud`).** Файл может «появиться» как метаданные до докачки. worker
  принудительно скачивает (`brctl download` / открытие файла) и проверяет, что это не `*.icloud`
  и размер стабилен. (OQ-3)
- **Формат аудио.** РЕШЕНО (PoC): декодировать `m4a` встроенным `afconvert` → wav 16k mono +
  `soundfile`, без внешнего ffmpeg (ADR-014). Запас — статический ffmpeg.
- **Пословные тайм-коды.** MLX-порт даёт SRT (посегментно); пословные — возможно только в torch
  GigaAM. Для точной привязки спикеров (Фаза 2) может потребоваться torch-ветка. (OQ-5)
- **Диаризация = PyTorch.** Фаза 2 возвращает torch-зависимость и HF-токен; +время обработки;
  качество на смешанной речи/перекрытии голосов под вопросом. (OQ-6)
- **Пропуск файлового события / сон компьютера.** Спасают подписка на `NSWorkspaceDidWake`
  (пересканирование после пробуждения) и периодический «подметающий» sweep приложения.
- **Холодный старт модели.** Доминирует на коротких файлах; лечится батчингом.
- **Сторонний MLX-порт.** Community-проект → риск поддержки/паритета; митигировано фолбэком на
  официальный `gigaam` и фиксацией версии.
- **Telegram как канал.** Транскрипт уходит на серверы Telegram — осознанный компромисс (NFR-1).

## 6. Технологический стек

- **iPhone:** Shortcuts (share-target, опционально), Voice Memos, iCloud Drive.
- **Mac — приложение в строке меню (Swift):** AppKit/SwiftUI; FSEvents; `NSWorkspace` (события сна);
  `UserNotifications` (уведомления); `SMAppService` (login item); упаковка в неподписанный `.dmg`.
  См. ADR-012.
- **Mac — worker (Python, спавнится Swift'ом как подпроцесс):** `gigaam-mlx` (MLX); `soundfile` +
  встроенный `afconvert` для декодирования аудио (без внешнего ffmpeg, ADR-014); HTTP-клиент для
  Telegram Bot API.
- **Mac (Фаза 2-3):** `pyannote.audio` (PyTorch), HF-токен; библиотека эмбеддингов для голос-ID.
- **Граница:** Swift ↔ Python только через подпроцесс (файл статуса / stdout / код возврата), не FFI.
- **Без:** VPS, БД, очередей, Docker (на старте) — намеренно, ради простоты (NFR-7).

## 7. Структура проекта (предполагаемая)

```
mlaud/
├── README.md
├── docs/{requirements,architecture,adr,ux-ui}.md
├── MLaudApp/                  # Swift-приложение (Xcode project)
│   ├── MenuBarController      # иконка, меню, статус
│   ├── FolderWatcher          # FSEvents + sweep-таймер
│   ├── WakeObserver           # NSWorkspaceDidWake → sweep
│   ├── WorkerRunner           # спавн Python-worker, чтение статуса
│   ├── SettingsView           # окно настроек (UserDefaults)
│   ├── Notifications          # UserNotifications
│   ├── LoginItem              # SMAppService (автозапуск)
│   └── Resources/python/      # упакованное Python-окружение worker'а (OQ-10)
├── worker/                    # Python ML-worker (эфемерный)
│   ├── worker.py              # вход: обработать пакет → выход
│   ├── transcribe.py          # gigaam-mlx (+ torch-фолбэк)
│   ├── diarize.py             # Фаза 2: pyannote
│   ├── speakers.py            # Фаза 3: база голосов
│   ├── telegram.py            # sendDocument / ошибки
│   └── pyproject.toml
├── build/                     # сборка .app и .dmg (create-dmg)
└── shortcuts/
    └── README.md              # как собрать Shortcut на iPhone (опционально)
```

Локальные данные (вне репозитория): `~/ASR/{ASROutput/AllOutputs, Processed/AllRecords, service}`.

## 8. Запасной транспорт (если iCloud не подойдёт)

Если iCloud-транзит окажется ненадёжным (переполнен/лаги):
- **Прямая отправка на Mac** по локальной сети (SSH/SMB/HTTP), когда Mac доступен; запись при этом
  всё равно остаётся в Voice Memos на телефоне как резерв (можно переотправить).
- **Через Telegram** как транспорт аудио (бот скачивает файл) — но лимиты бота на размер файла
  (~20-50 МБ) делают это ненадёжным для длинных записей.

iCloud-транзит выбран как основной (ADR-004): нулевая настройка, авто-синхронизация, файлы не
теряются. Альтернативы — на случай, если основной путь не оправдает себя.

> Структура и решения — ориентир этапа проектирования, не финал.
