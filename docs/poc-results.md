# Результаты PoC (GigaAM-v3 MLX на M5)

Проверочный прогон на реальном железе пользователя (MacBook M5, macOS 26.5, arm64).
Окружение: uv venv c Python 3.12, `gigaam-mlx` (MLX 0.31.2). Тестовое аудио — синтез через
`say -v Milena` (русская речь), сконвертировано в m4a через `afconvert` (имитация Voice Memos).

> Оговорка: тест на TTS-аудио проверяет **механику и скорость**, но не реальную точность на живой
> речи (TTS коверкает английские термины). Финальную оценку точности делать на реальной записи.

## Сводка: открытые вопросы закрыты

| OQ | Вопрос | Результат |
|---|---|---|
| **OQ-1** | формат m4a / ffmpeg | `gigaam-mlx` внутри **всегда зовёт ffmpeg**. Декодирование без ffmpeg: **`afconvert`** (m4a→PCM wav) + `soundfile` + **ресемплинг `soxr` до 16к**. ⚠️ `afconvert -r` НЕ ресемплит надёжно — читать реальную частоту и ресемплить в Python (см. «Критический баг»). Проверено на реальном 48к-файле. |
| **OQ-2** | длинные файлы / VAD | MLX-порт **сам режет длинное аудио** по тишине (`split_audio`, чанки ~20с). 146с → 9-14 сегментов. **pyannote/VAD для транскрипции не нужен** (он только для диаризации, Фаза 2). |
| **OQ-4** | вариант / скорость | Steady-state: **CTC ~107x RT, RNNT ~85x RT**. Холодный спавн процесса ≈ **1.5с**. Разовая компиляция Metal-кернелов ~34с — **кэшируется на диск, один раз на машину**. Скорость — не узкое место. |
| **OQ-5** | тайм-коды | **Посегментные** тайм-коды есть (SRT). **Пословных в MLX нет** (нужна torch-версия). Для MVP посегментных достаточно. |

## Важные находки

- **Модель реально e2e.** Репозитории весов: `aystream/GigaAM-v3-e2e-ctc-mlx` и
  `…-e2e-rnnt-mlx`. → **пунктуация + нормализация чисел из коробки** («21 июня», не «двадцать первое»).
- **HF-токен НЕ нужен** для скачивания весов MLX-модели (только предупреждение о rate-limit).
  Токен потребуется лишь для pyannote в Фазе 2.
- **Эфемерный процесс подтверждён.** Полный холодный старт (импорты + загрузка модели + warmup на
  9с аудио) = **1.46с реального времени**. Память освобождается при выходе. ADR-005 валиден.
- **Скорость не проблема.** Дневной объём (≤5ч аудио) распознаётся за **секунды-десятки секунд**
  компьюта.

## Замеры скорости (фактические)

```
model load:                  ~0.6–0.8 c
warmup (1-й инференс/процесс): ~0.7 c (Metal-кернелы уже в дисковом кэше)
короткий файл  (9с):  CTC 0.0–0.7c | RNNT 0.1–0.7c
длинный файл (146с):  CTC 1.4c (107x RT, 9 сегм.) | RNNT 1.7c (85x RT, 9 сегм.)
полный холодный спавн процесса (короткий файл): real 1.46c
разовая компиляция Metal (1-й запуск на машине): ~34c (далее из кэша)
```

## Качество (на TTS-аудио — ориентир, не финал)

- **Русский — отлично.** Короткая фраза почти идеально, с пунктуацией.
- **Слабое место — английские/собственные термины:** Plaud→«плот», Voice Memos→«Mamos/сМС»,
  Apple Silicon→«Piliten», GigaAM→«Gigom». Частично это вина TTS (коверкает английский).
- **RNNT чуть точнее CTC** на собственных именах (получил «Macbuk», «Telegram», «iCloud»);
  CTC их искажал сильнее. → под цель «максимальная точность» берём **RNNT**.
- Многие ошибки в терминах закроет **постобработка в LLM** (план пользователя).

## Решения для реализации (из PoC)

1. **Аудио-декодирование:** использовать встроенный **`afconvert`** (m4a→wav 16k mono) + `soundfile`,
   патчить `load_audio` в worker'е. Нулевые внешние зависимости, нативно для macOS.
   (Запасной вариант — бандлить статический ffmpeg из `imageio-ffmpeg`.)
2. **Движок:** **RNNT** (e2e) как целевой; CTC — если понадобится максимальная скорость.
3. **Длинные файлы:** полагаться на встроенный `split_audio`; VAD/pyannote не тащить в MVP.
4. **Тайм-коды:** посегментные (SRT) для MVP. Пословные — только если потребуются для диаризации.
5. **Worker сам создаёт выходные папки** (CLI `--output-dir` их не создаёт — баг порта).
6. **Кэш моделей:** качать при первом запуске; держать в стабильном месте (`~/ASR/service/` или
   HF-кэш). Первый-в-жизни запуск платит ~34с компиляции Metal — разово.

## ⚠️ Критический баг и урок реализации: ресемплинг

На реальной записи (48 кГц) первый прогон выдал **полный мусор** (~40 бессвязных слов за 14 мин).
Причина: `afconvert -r 16000` **не выполнил ресемплинг** (вернул те же 48 кГц), а код считал, что это
16 кГц → модель получала аудио в **3× быстрее** → мел-спектрограмма (рассчитана на 16 кГц) сломалась.
На коротких TTS-тестах баг проскочил (там было 22 кГц, расхождение лишь 1.4×, чистая речь «вытянула»).

**Урок для worker'а:** НИКОГДА не предполагать частоту дискретизации. Декодировать через `afconvert`
в PCM (любая частота) → прочитать **фактическую** частоту через `soundfile` → ресемплить до 16 кГц
через `soxr` (уже в зависимостях). Закреплено в ADR-014.

## Тест на РЕАЛЬНОЙ записи (после фикса)

Файл: `Пример записи.m4a` — реальная запись Voice Memos, **48 кГц mono, 13:48 (829 c)**,
деловой диалог.

- **Скорость:** 829 c аудио → **10.6 c** инференса = **78× realtime** (RNNT). 56 сегментов с тайм-кодами.
- **Качество — высокое.** Связный, читаемый русский с пунктуацией и оформлением реплик диалога.
  Доменные термины распознаны в основном верно.
- **Слабые места (мелкие):** собственные имена и придуманное название инструмента
  (фамилии и названия инструментов гуляют, «корсфункциональный»). → закрывается LLM-постобработкой.
- **Вывод:** на живой русской речи RNNT даёт рабочий результат «из коробки»; TTS-тест занижал точность.

## Что НЕ проверено (осознанно)

- Поведение на **очень** длинном файле (1-2 часа) и пиковая память — экстраполируется как линейное.
- Запись с сильным шумом / несколькими далёкими говорящими.
- Диаризация pyannote (Фаза 2) — отдельный PoC позже.
