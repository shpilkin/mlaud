# Распределение транскриптов по проектам — сторона mlaud

**Канонический документ фичи — в репозитории Niti:** `email_reader/docs/feature-routing.md`.
Там модель данных, классификация, структура папки проекта, этапы. Здесь — только то, что делает
mlaud, потому что 90% работы лежит на стороне роутера.

## Почему mlaud почти не меняется

Маршрутизацией занимается Niti (`email_reader`): у него уже есть реестр проектов
(`Project` = имя + папка + промт), мульти-лейбл классификатор, `ActionItem` с трассировкой до
источника, UI правки и аудит. Заводить второй реестр внутри mlaud — гарантированный дрейф:
поправил промт проекта в одном приложении, маршрутизация в другом стала врать.

**mlaud остаётся тем, чем был: транскрибирует и сдаёт результат.** Он не классифицирует, не знает
про проекты и ничего не пишет в их папки.

```
mlaud: аудио → транскрипт → ~/ASR + Telegram + json в инбокс роутера
                                                      │
Niti:                          инбокс → Meeting → классификация → папки проектов
```

## Контракт

### Сайдкар рядом с транскриптом

```
~/ASR/ASROutput/AllOutputs/<YYYY-MM>/<base>.meta.json
```

Только то, что известно до маршрутизации: `meeting_id`, `started_at`, `duration`, пути к
транскрипту и аудио. Проектов, уверенности и причин здесь нет и не будет — их определяет Niti,
и **Niti в `~/ASR` не пишет вообще**. Один файл — один писатель.

### Передача роутеру

```
~/Library/Application Support/EmailReader/artifacts_inbox/<meeting_id>.json
```

```json
{
  "meeting_id": "0123456789abcdef",
  "started_at": "2026-08-16T14:30:05+03:00",
  "duration_sec": 2820,
  "asr_root": "/Users/<user>/ASR",
  "transcript_path": "ASROutput/AllOutputs/2026-08/2026-08-16_14-30-05.txt",
  "srt_path":        "ASROutput/AllOutputs/2026-08/2026-08-16_14-30-05.srt",
  "audio_path":      "Processed/AllRecords/2026-08/2026-08-16_14-30-05.m4a",
  "source": "mlaud"
}
```

- `meeting_id` — **из содержимого аудио** (первые 16 hex от sha256), не из имени файла:
  переименование не должно порождать вторую встречу.
- Пути **относительные** от `asr_root`. Абсолютный путь умрёт при переносе архива.
- **Запись атомарная:** во временный файл, потом `rename`. Иначе роутер прочитает половину.
- Удаляет json **Niti**, после того как поставит событие в очередь. mlaud его не трогает.
- Niti не запущен → json ждёт. Та же развязка, что iCloud-inbox даёт для аудио.

### Время начала записи

Единственная нетривиальная часть. Реализовано в `mlaud_worker/artifact.py`, источник пишется
в сайдкар полем `started_at_source` — иначе непонятно, чему верить:

1. метаданные аудио — бокс `mvhd` (`creation_time`, UTC);
2. полная метка времени **в имени файла**, если она там есть;
3. `mtime − duration`;
4. `mtime`.

Пункты 2 и 3 поменялись местами относительно первоначального замысла, и вот почему. Замысел
опирался на то, что «`mtime` — это конец записи»; на файлах архива это неверно. У
`New Recording 13.m4a` длительность 32 минуты, а `mtime` **на 5 секунд позже**
`creation_time`: это момент финализации файла, то есть примерно начало. Вычитать из него
длительность — уехать на полчаса назад. Имя же, в котором метка ЕСТЬ, — точное свидетельство:
у `31 Dec 2025 at 20:55:55.m4a` оно совпало с `mvhd` до секунды (17:55:55 UTC = 20:55:55 MSK).
Имена без метки (`New Recording 20`) просто не совпадают с шаблоном и идут дальше по цепочке —
исходное опасение «имена врут» этим и снимается.

`creation_time` читается как UTC (так велит ISO/IEC 14496-12) — проверено на том же файле с
меткой в имени.

С отказом от календаря как сигнала (R-5 в каноническом доке) точность времени перестала быть
гейтом — она нужна для имени заметки, сортировки и `meeting_id`. Но брать её из имени файла всё
равно нельзя.

## Чего mlaud не делает

- не классифицирует и не хранит принадлежность проектам;
- не пишет в папки проектов;
- **не сообщает в Telegram, куда встреча разложена.** Уведомление уходит сразу после
  транскрипции, а маршрутизация происходит позже и в другом процессе — на этот момент проекты
  неизвестны и стать известными не могут. О раскладке сообщает Niti, там же и ссылка на правку.

## Инварианты

1. **Сбой роутера не ломает конвейер.** Транскрипция, доставка в Telegram и архивация
   отрабатывают, даже если Niti не запущен и инбокс недоступен. Дисциплина та же, что у доставки:
   попытка, лог, дальше. `process_file()` уже устроен так, что архивация идёт **всегда**, даже при
   провале доставки (`pipeline.py:139`).
2. **Только добавляем.** Транскрипт и аудио не двигаются и не удаляются.
3. **Один писатель в `~/ASR`** — mlaud.

## Правки

Все четыре сделаны (модуль `mlaud_worker/artifact.py`, тесты `tests/test_artifact.py` и
`tests/test_pipeline.py`):

1. ✅ Честный `started_at` — метаданные аудио (`mvhd`), не имя файла.
2. ✅ `<base>.meta.json` рядом с транскриптом — пишется всегда, даже когда обмен выключен.
3. ✅ json в `artifacts_inbox`: атомарно (во временный файл, затем `rename`), и сбой сдачи
   никогда не роняет конвейер — статус попадает в результат прогона (`artifact`).
4. ✅ В `Config` — `router_inbox` (переопределяется `MLAUD_ROUTER_INBOX`).

**Включение без настройки.** По умолчанию `router_inbox` указывает на штатный каталог данных
Niti. Если роутер не установлен (каталога нет) — сдача пропускается со статусом `no-router`, и
папка не создаётся: копить json там, где их никто не читает, незачем. Dev-конфигурация Niti с
переопределённым каталогом данных задаёт `MLAUD_ROUTER_INBOX`.

**Проверено сквозняком:** worker обработал реальную запись из архива → сайдкар и json в папке
обмена → Niti забрал json, завёл встречу (`0123456789abcdef`,
829 с — из метаданных аудио, не из имени и не из `mtime`), удалил json, вытащил заголовок из
расшифровки; пути к транскрипту и аудио резолвятся от корня архива.
