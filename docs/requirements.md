# Требования

## 1. Контекст и цель

Личный инструмент одного пользователя для автоматической транскрипции голосовых записей
(встречи, заметки) с iPhone. Замена платному Plaud в части софта. Транскрипция выполняется
локально на MacBook Pro (M5, 48 ГБ). Готовый текст с тайм-кодами доставляется файлом в Telegram.
Аудио и транскрипты хранятся локально на Mac.

### Профиль использования
- Один пользователь.
- **3-5 записей в день**, длительность от пары минут до ~1-2 часов.
- Верхняя оценка нагрузки: ~5 часов аудио в день.
- Язык: **русский ~90% + английский вперемешку** (в т.ч. в пределах одной фразы).
- Ноутбук **обычно при пользователе**, но не обязан быть онлайн в момент записи.

## 2. Фазы

- **MVP:** распознавание + тайм-коды + локальное хранение + доставка файлом в Telegram.
- **Фаза 2:** диаризация (метки «Спикер N»).
- **Фаза 3:** идентификация спикеров по голосу с пользовательскими именами.
- **Сквозное:** архитектурный задел под авто-суммаризацию (выполняется вручную на старте).
- **Фаза 4:** приложение с главным окном в дизайн-системе Niti (FR-11, [ux-app.md](ux-app.md)).
- **Фаза 5:** суфлёр — живой звонок, подсказки по брифу, итоги (FR-12,
  [feature-prompter.md](feature-prompter.md)). План — [task-app-ui-and-prompter.md](task-app-ui-and-prompter.md).

## 3. Функциональные требования

### FR-1. Захват аудио на iPhone
- FR-1.1. **Единственный режим:** запись в штатном **Voice Memos** (фон, заблокированный экран,
  любая длительность). Используется и для коротких, и для длинных записей.
- FR-1.2. Контракт системы — **папка inbox**, а не Shortcut. Файл может попасть туда:
  через Shortcut (рекомендуется, авто-маршрутизация) **или** вручную «Поделиться → Сохранить в Файлы».
- FR-1.3. Заголовок при записи **не запрашивается**. Имя файла — авто по дате/времени.
- FR-1.4. Back Tap и отдельный «короткий» режим записи — **не реализуются** (отменены).

### FR-2. Транспорт аудио (транзит через iCloud)
- FR-2.1. Аудиофайл попадает в папку **iCloud Drive** `ASR/ASRInbox/AllRecords/`.
- FR-2.2. Имя файла включает **дату и время**: `YYYY-MM-DD_HH-MM-SS.<ext>`.
- FR-2.3. iCloud используется **только как транзит**: Mac забирает файл на локальный диск и
  **удаляет его из iCloud** после успешного приёма. В iCloud ничего постоянно не копится.
- FR-2.4. Файл не должен теряться, если Mac недоступен — он ждёт в inbox до приёма.

### FR-3. Обнаружение новых файлов на Mac
- FR-3.1. На Mac постоянно работает лёгкое **приложение в строке меню** (см. FR-10), отслеживающее
  `iCloud/ASR/ASRInbox/AllRecords` через FSEvents.
- FR-3.2. Обработка запускается при появлении файлов, **при пробуждении из сна**
  (`NSWorkspaceDidWake`) и периодическим sweep'ом — разгребается накопившийся бэклог.
- FR-3.3. Приложение не держит модель в памяти; обработку выполняет отдельный подпроцесс (NFR-2).

### FR-4. Транскрипция
- FR-4.1. Движок — **GigaAM-v3**, MLX-порт; целевой вариант — **`rnnt`** (точность в приоритете).
  Допустимы `e2e_rnnt` (пунктуация/нормализация) или `ctc` (скорость) — выбор по бенчу (OQ-4).
- FR-4.2. Обработка идёт **пакетом**: модель грузится один раз на прогон, обрабатываются все
  накопившиеся файлы, процесс завершается.
- FR-4.3. Поддержка длинных файлов (десятки минут / часы) и смешанного RU/EN.
- FR-4.4. **Тайм-коды обязательны** (как минимум посегментные, SRT). Пословные — желательны
  (нужны для точной привязки к спикерам в Фазе 2), берутся из torch-версии при необходимости.

### FR-5. Хранение результатов (локально на Mac)
- FR-5.1. Транскрипт сохраняется **локально** в `~/ASR/ASROutput/AllOutputs/<дата>/` в форматах:
  `.txt` (с тайм-кодами, человекочитаемый), `.srt` и/или `.json` (тайм-коды для машинной обработки).
- FR-5.2. Файлы организованы по дате (папка на дату).
- FR-5.3. **Аудио хранится локально** в `~/ASR/Processed/AllRecords/<дата>/`, **не в iCloud**.
- FR-5.4. Из inbox (iCloud) обработанный файл удаляется после копирования на локальный диск,
  чтобы исключить повторную обработку и не забивать iCloud.
- FR-5.5. Служебные данные (логи, состояние, lock, кэш моделей) — в `~/ASR/service/`.

### FR-6. Доставка результата
- FR-6.1. По завершении обработки транскрипт отправляется в **Telegram** через бота.
- FR-6.2. Отправка **всегда файлом** (`.txt` с тайм-кодами), а не текстом сообщения.
- FR-6.3. При **ошибке** обработки пользователь получает уведомление в Telegram с причиной
  (молчаливый провал недопустим).

### FR-7. Диаризация — Фаза 2
- FR-7.1. После распознавания — разметка «кто-когда говорил» через **pyannote**
  (`speaker-diarization-3.1`); требуется HuggingFace-токен.
- FR-7.2. Результат — транскрипт с метками «Спикер 1/2/...» и тайм-кодами.
- FR-7.3. Допустим облегчённый «гибрид» (VAD + эмбеддинги + кластеризация) как опция, если pyannote
  окажется тяжёлым/неточным.

### FR-8. Идентификация спикеров по голосу — Фаза 3
- FR-8.1. База **голосовых отпечатков** (эмбеддингов) известных людей с заданными пользователем
  именами/пометками (enrollment).
- FR-8.2. При обработке кластеры спикеров сопоставляются с базой → в транскрипте проставляются
  **реальные имена** вместо «Спикер N».
- FR-8.3. Неизвестный голос остаётся анонимным «Спикер N» с возможностью позже добавить в базу.
- FR-8.4. Кластеру с суммарной речью **менее 30 c** имя не подставляется никогда, независимо от
  порога: в таком фрагменте нет сигнала о говорящем (замер, [feature-speaker-id.md](feature-speaker-id.md) §1).
- FR-8.5. Порог узнавания настраивается пресетами; стартовые значения из замера —
  строго 0.80 / сбалансировано 0.75 / мягко 0.70.
- FR-8.6. Разметка голосов — в окне «Голоса» по карточкам кластеров последних записей
  (образец аудио, цитата, объём речи, текущее узнавание), без просмотрщика транскрипта и без
  терминала. Данные карточек worker сохраняет при обработке (сайдкар и клипы,
  [feature-speaker-id.md](feature-speaker-id.md) §6.2); повторная диаризация не нужна.
- FR-8.7. Управление базой в том же окне: люди и образцы, переименование, удаление образца и
  человека целиком. Переподпись транскрипта текущими именами и повторная отправка в Telegram —
  по кнопке, не автоматически.

### FR-9. Суммаризация — сквозной задел
- FR-9.1. На старте суммаризация **ручная** (пользователь сам прогоняет текст в LLM).
- FR-9.2. Архитектура оставляет **точку расширения** для авто-суммаризации (шаг после транскрипции)
  без переделки конвейера.

### FR-10. Приложение и интерфейс (menu bar app)
- FR-10.1. Поставляется как **macOS-приложение** в **.dmg**, запускается двойным кликом, **не из
  терминала**.
- FR-10.2. Живёт в **строке меню** с иконкой, отражающей состояние (ожидание / обработка / готово /
  ошибка / пауза).
- FR-10.3. Меню: текущий статус, последние результаты (клик → открыть транскрипт), «Обработать
  сейчас», «Открыть папку транскриптов», «Пауза слежения», «Настройки…», «Запускать при входе»,
  «Выход».
- FR-10.4. Окно **настроек**: пути папок (+ автосоздание структуры), Telegram (token, chat_id, тест),
  вариант модели, диаризация+HF-токен (Фаза 2), флаги поведения, автозапуск при входе.
- FR-10.5. **Системные уведомления** macOS об успехе/ошибке (в дополнение к Telegram).
- FR-10.6. **Автозапуск при входе** (login item), чтобы приложение всегда работало.
- FR-10.7. Приложение **переживает сон/пробуждение** компьютера и обрабатывает накопленное после
  выхода из сна (см. FR-3.2).
- FR-10.8. Первый запуск — onboarding: папки, Telegram, разрешения macOS (уведомления, доступ к диску).

### FR-11. Главное окно приложения — Фаза 4
- FR-11.1. У приложения есть **главное окно** с сайдбаром; вся функциональность доступна из
  окна. Строка меню остаётся для статуса и быстрых действий; FR-10.3 сокращается до
  [ux-app.md](ux-app.md) §5.
- FR-11.2. Визуальный язык — дизайн-система Niti через общий пакет `NitiUI` (ADR-018, ADR-019).
- FR-11.3. Разделы: Обзор, Записи, Суфлёр, Голоса, Диктовка, iPhone, Уведомления, Настройки
  ([ux-app.md](ux-app.md) §3–4). Поведение существующих функций не меняется.
- FR-11.4. **Записи**: список обработанных записей из архива (дата, длительность, говорящие,
  метки) с открытием транскрипта, `.srt`, аудио и итогов. Без поиска по тексту (§5).
- FR-11.5. **Обзор**: состояние конвейера, очередь и докачка iCloud, последние результаты,
  карантин с повтором, очередь доставки, состояние iPhone/диктовки/голосов.
- FR-11.6. Настройки во вкладках; применение сразу при изменении; предупреждения инлайн.
- FR-11.7. Иконка в Dock — пока окно открыто; закрытие окна не завершает приложение
  (слежение, приём с телефона и горячая клавиша продолжают работать).
- FR-11.8. Минимальная версия macOS — 14.2 (ADR-020).

### FR-12. Суфлёр — Фаза 5
Полная формулировка — [feature-prompter.md](feature-prompter.md) §3. Сводка:
- FR-12.1. Два режима захвата: **ВКС** (микрофон = «Я», звук приложения звонка =
  «Собеседник») и **офлайн** (один микрофон, несколько людей). Предупреждение об эхе без
  наушников; подавление эха — вне v1 (OQ-17).
- FR-12.2. Живой транскрипт обеих сторон: финальный текст фразы ≤ 1.5 с после её конца,
  хвост отдельно; пишется на диск по ходу.
- FR-12.3–12.5. **Бриф** (цель, собеседник, повестка с планом минут, скрипт/методология,
  ожидаемая длительность, режим), **профиль** «кто я» (один файл), **материалы** (файлы в
  папке брифа, в т.ч. расшифровки из архива; бюджет в токенах). Шаблоны по ролям.
- FR-12.6–12.8. **Карточки** семи типов (ответ, вопрос, факт, следующий шаг, ушли с
  маршрута, напряжение, время), ≤ 140 символов, ≤ 4 за раз; повестка с состояниями;
  таймер; `time`-карточки на 50/80/100 % считаются локально; «Подсказать», пауза, закрепить,
  заметки.
- FR-12.9. Компактная плавающая панель поверх окон, не забирающая фокус.
- FR-12.10. **Итоги** после звонка: результат по цели, содержание, решения, шаги, открытые
  вопросы, оценка по критериям шаблона; отправка в Telegram.
- FR-12.11. Запись звонка идёт через inbox и штатный конвейер; для ВКС — стерео + сайдкар
  каналов, транскрипция по каналам без диаризации; артефакт Niti получает блок `prompter`.
- FR-12.12. Офлайн: **живая пометка** говорящих по базе голосов с неуверенностью; не
  идентификация, FR-8.9 без изменений; канон — пакетная диаризация после встречи.
- FR-12.13–12.14. Подключение модели (Anthropic или OpenAI-совместимый эндпоинт, ключ в
  Keychain), лимит запросов в минуту, потолок стоимости на звонок, стоимость по ходу.
- FR-12.15. Напоминание о согласии на запись при старте.
- FR-12.16. Деградация: без модели, сети, разрешения на звук приложения или при падении
  распознавателя звонок и запись продолжаются.

## 4. Нефункциональные требования

### NFR-1. Приватность
- Аудио и транскрипты **не уходят в сторонние сервисы транскрипции**; обработка локальная.
- Все модели (GigaAM, pyannote) работают **локально** на Mac.
- Осознанные исключения: iCloud Drive (краткий транзит аудио) и Telegram (доставка транскрипта).
- HF-токен нужен только для скачивания весов pyannote; инференс — локальный.
- **Исключение (Фаза 5, ADR-022):** подсказчик суфлёра отправляет транскрипт звонка и материалы
  брифа в выбранную модель — в том числе облачную. Включается на бриф, по умолчанию выключен;
  распознавание и запись остаются локальными; локальная модель поддерживается тем же кодом.

### NFR-2. Управление памятью
- Память под ML-модели занимает RAM **только во время обработки** и освобождается после.
- Постоянно живущий компонент (watcher) потребляет память близко к нулю.
- Резидентные процессы (диктовка, живой звонок, подсказчик) живут только во время сессии и
  закрываются по идл-таймауту; живой звонок использует **одну** загруженную модель на все
  каналы (ADR-023).

### NFR-3. Стоимость
- Целевая стоимость эксплуатации — **$0** (имеющееся железо, бесплатный Telegram-бот, бесплатные
  open-source модели). Никаких платных API.
- **Исключение (Фаза 5, ADR-022):** облачная модель суфлёра платная. Стоимость видна по ходу
  звонка, потолок на звонок и лимит запросов в минуту — в настройках.

### NFR-4. Надёжность
- Записи не теряются: файл живёт в `inbox`, пока успешно не принят на локальный диск.
- Повторный запуск не обрабатывает один файл дважды (состояние выражено расположением файлов).
- Параллельные запуски watcher'а защищены лок-файлом.

### NFR-5. Задержка
- Обработка **не обязана быть мгновенной**: допустима задержка «обработается, когда Mac доступен и
  синхронизировал файл из iCloud».
- При доступном Mac обработка дневного объёма должна укладываться в единицы минут компьюта
  (диаризация в Фазе 2 добавит время — измерим).
- **Живой режим (Фаза 5):** финальный текст фразы — не позже 1.5 с после её конца; карточка
  подсказки — целевой коридор 3 с после конца фразы собеседника (замер S5, OQ-16). Захват и
  распознавание не блокируют главный поток (как в диктовке).

### NFR-6. Ограничение на iCloud
- iCloud Drive почти заполнен → транзитный файл должен удаляться **сразу** после приёма.
- Риск: если iCloud переполнен, даже транзит может не синхронизироваться (см. архитектуру, риски).

### NFR-7. Простота сопровождения
- Минимум инфраструктуры: без VPS, без очередей (Celery/Redis), без БД на старте.
- Конфигурация и секреты (токен Telegram, `chat_id`, HF-токен) — в `.env`, не в коде.

## 5. Явно вне области (Out of scope)

- Облачная транскрипция (Яндекс SpeechKit, OpenAI Whisper API) — отклонено, см. ADR-001.
- Веб-интерфейс / поиск по архиву / теги.
- Многопользовательский режим, масштабирование.
- Мгновенная транскрипция «на ходу» без участия Mac.
- Хранение аудио/транскриптов в iCloud (только локально на Mac).
- Суфлёр: любые действия от имени пользователя (ответы в чат, письма, звонки) — он только
  показывает; перевод в реальном времени; суфлёр на iPhone; редактор транскриптов.
- Реестр людей и проектов внутри mlaud — это Niti (ADR-021).

## 6. Открытые вопросы

Подробности по закрытым — в [poc-results.md](poc-results.md).

- ~~OQ-1. Формат m4a / ffmpeg~~ → **ЗАКРЫТО:** декодировать встроенным `afconvert` (m4a→wav) +
  `soundfile`, без внешнего ffmpeg.
- ~~OQ-2. Длинные файлы / VAD~~ → **ЗАКРЫТО:** MLX-порт сам режет по тишине; VAD/pyannote для
  транскрипции не нужен. HF-токен для скачивания весов **не требуется**.
- OQ-3. Поведение iCloud Drive с «не скачанными» файлами-плейсхолдерами (`.icloud`). *(к реализации)*
- ~~OQ-4. Вариант / скорость~~ → **ЗАКРЫТО:** целевой **RNNT** (e2e); скорость 85-107x RT, спавн ~1.5с.
- ~~OQ-5. Тайм-коды~~ → **ЗАКРЫТО:** посегментные (SRT) есть; пословных в MLX нет (для MVP хватает).
- OQ-6. Качество pyannote-диаризации на смешанной RU/EN речи и при перекрытии голосов (Фаза 2).
  *(частично измерено:* на архиве из 15 записей **19% кластеров оказались смесью двух голосов**,
  в многолюдных встречах до 40–55%. Это верхняя граница для Фазы 3: такому кластеру нельзя
  поставить имя. Отдельно RU/EN не выделялось — весь архив смешанный.*)*
- ~~OQ-11. Отдаёт ли pyannote эмбеддинги кластеров и хватает ли их для узнавания между файлами~~
  → **ЗАКРЫТО:** `return_embeddings=True` работает в 3.1.1; узнавание между файлами измерено
  (ADR-016).
