# S2 — звук приложения звонка: process tap против ScreenCaptureKit. Результат

**Дата:** 2026-09-05 · **Вопрос:** OQ-13 / OQ-P1 — какой захват даёт звук только одного
приложения, какое разрешение просит, переживает ли пересборку, что с форматом и нагрузкой.
Машина: MacBook Pro, macOS 26.5.2, встроенные динамики и микрофон.

**Вердикт: ScreenCaptureKit с фильтром по приложению. Обе ветки изолируют звук по
процессу до цифровой тишины (−inf dBFS при звучащем рядом тоне −9 dBFS) и переживают
пересборку с подписью «MLaud Local Signing» без нового диалога — гейт пройден обеими.
Решает браузер: у Safari звук выводит вспомогательный процесс (WebKit GPU; у Chrome по
списку процессов, вероятно, так же), tap на PID главного процесса не даёт ни кадра, SCK по
приложению даёт речь. Плата за SCK — разрешение «Запись экрана» и перезапуск приложения после первого
согласия.**

## Проба

- `probe/` — Swift-проба, бандл `ru.mlaud.appaudio-probe` (`LSUIElement`,
  `NSAudioCaptureUsageDescription`, `NSMicrophoneUsageDescription`); `build.sh <номер>`
  собирает `~/ASR/spikes/appaudio/AppAudioProbe.app` и подписывает «MLaud Local Signing»
  (designated requirement: identifier + certificate leaf), номер попадает в
  `CFBundleVersion` и в бинарь, чтобы пересборка была настоящей.
- Ветка (а) `TapCapture.swift`: `kAudioHardwarePropertyTranslatePIDToProcessObject` →
  `CATapDescription(stereoMixdownOfProcesses:)` (private, unmuted) →
  `AudioHardwareCreateProcessTap` → агрегатное устройство (private, список tap'ов,
  поддевайс — устройство вывода по умолчанию; `--tap-only` — без поддевайса) →
  `AudioDeviceCreateIOProcIDWithBlock`. Ветка (б) `SCKCapture.swift`: `SCShareableContent`
  → `SCContentFilter(display:including:[app])` → `SCStream` только с аудио-выходом
  (видео 2×2, 1 кадр/с, `excludesCurrentProcessAudio`).
- `main.swift` пишет журнал: RMS и пик по каналам за каждую секунду, число кадров,
  события (смена устройства вывода, уход процесса, формат, ошибки потока), CPU из
  `getrusage`, WAV. Запуск через `open --stdout`, как у настоящего приложения — иначе
  разрешения спрашивались бы у терминала.
- `run.sh <tap|sck> <isolation|control|switch|rebuild> [флаги пробы]`: «приложение
  звонка» — QuickTime Player с речью (`clip-a.txt`, голос Милена, 31 с, −17 dBFS),
  «другое приложение» — `afplay` с тоном 880 Гц (`tone.py`, 10 с, −9 dBFS);
  `summarize.py` сводит журнал по окнам сценария. Журналы и WAV — в
  `~/ASR/spikes/appaudio/`.

## Изоляция (сценарий isolation, 62 с)

Окна: тишина → речь → речь + тон из `afplay` → речь → тишина → тон один → выход
QuickTime. RMS dBFS (оба канала одинаковы), «—» — кадров не было.

| ветка | тишина | речь | речь + тон | речь | тишина | **тон один** | **после выхода** | CPU |
|---|---|---|---|---|---|---|---|---|
| tap по PID | — | −16.8 | −16.5 | −17.5 | −inf | **−inf** | **−inf** | 1.0 % |
| SCK по приложению | −inf | −16.9 | −16.5 | −17.4 | −inf | **−inf** | **−inf** | 1.1 % |
| tap `--all` (контроль) | — | −16.9 | −8.4 | −17.1 | −inf | −9.1 | −inf | 1.1 % |
| SCK `--all` (контроль) | −inf | −16.9 | −8.3 | −17.4 | −inf | −9.2 | −inf | 1.4 % |

Контроль показывает, что тон доходит до точки захвата на −9 dBFS; в режиме «одно
приложение» те же окна — не −60, а ровно нули: подавление полное. Попутно: SCK «весь
дисплей» захватывает и `afplay`, у которого окон нет.

## Браузер: звук во вспомогательном процессе

Safari играет `A.aiff` (`open location`, автозапуск). Список процессов Core Audio
(`Probe list`): `Safari` pid 1438 `output=0`, «Safari Graphics and Media»
(`com.apple.WebKit.GPU`) pid 1450 `output=1`. Три захвата одновременно по 8 с:

| захват | результат |
|---|---|
| tap `--pid 1438` (главный процесс Safari) | 0 кадров, IOProc не стартовал |
| tap `--pid 1450` (WebKit GPU) | речь, −17 dBFS |
| SCK `--app Safari` | речь, −17 dBFS |

У Chrome по списку процессов, вероятно, так же (объекты есть и у `Google Chrome`, и у
`com.google.Chrome.helper`, звук в нём не проигрывался — не проверено). Для tap пришлось бы
собирать все вспомогательные процессы приложения: ответственный PID — приватный API, а
по префиксу bundle id хелпер Safari (`com.apple.WebKit.GPU`) не находится. SCK относит
звук к приложению сам. Zoom, Teams и прочие клиенты ВКС не установлены — на них не
проверялось; Telegram в списке Core Audio один процесс.

## Разрешения и пересборка

| | tap | SCK |
|---|---|---|
| диалог | «Запись системного звука» (ключ `NSAudioCaptureUsageDescription`); появляется на `AudioDeviceStart`, вызов блокируется до ответа (5.5 с в прогоне 1), после «Разрешить» захват идёт в том же процессе | «Запись экрана»; первый `SCShareableContent` сразу (70 мс) возвращает −3801 «пользователь отклонил», система показывает диалог, после согласия нужен перезапуск приложения — второй запуск: READY через 0.19 с |
| пересборка | сборки 1 → 2 → 152828 → 153138: без диалога, READY 0.07–0.08 с | сборки 1 → 2 → 152828 → 153155: без диалога, READY 0.19 с |
| панель настроек | не проверено глазами: база TCC из сессии недоступна (`authorization denied`); в macOS 15+ обе категории живут в панели «Запись экрана и системного звука» | |

Микрофон (для замера эха) — отдельный диалог «Микрофон», 1.8 с.

## Формат, старт данных, поведение

| | tap | SCK |
|---|---|---|
| формат | float32 48 кГц 2ch interleaved — частота устройства, tap не ресемплирует; блоки 512 кадров (10.7 мс) | float32 non-interleaved, по буферу на канал; 48 кГц 2ch → 960 кадров (20 мс); запрос 16 кГц mono выполняется: 16000 Гц 1ch, 320 кадров |
| старт данных | кадры идут только с первого звука процесса — `first_io` совпадает с `play` (2.4 / 5.5 / 10.8 с), до этого 0 кадров; `--tap-only` так же | тишина идёт с 0.12 с после `startCapture` непрерывно, порциями 48000–50880 кадров/с |
| выход приложения | IOProc продолжает отдавать тишину, событий от HAL нет | поток продолжает отдавать тишину, `didStopWithError` не приходит |
| уход процесса | обе ветки узнают только опросом `kill(pid, 0)` | |
| смена устройства вывода | **не измерено**: в прогонах `switch` события `default_output_changed` не было — вывод на наушники не переключался | **не измерено** |

## Эхо динамиков (FR-12.1)

Микрофон встроенный, 48 кГц; прогон `tap isolation --mic` через динамики: тишина
−62 dBFS, речь из динамиков −47, тон −50, после выхода QuickTime −69. Динамики
попадают в микрофон на 15 dB выше пола — предупреждение FR-12.1 оправдано. На
наушниках не измерено (см. выше).

## Подводные камни, найденные пробой

- `CMSampleBufferGetAudioBufferListWithRetainedBlockBuffer` со списком на 8 буферов
  (136 байт) отдаёт −12737 `ArrayTooSmall`; нужный размер (40 байт для двух буферов)
  надо спросить первым вызовом с `bufferListOut: nil`.
- `AudioObjectRemovePropertyListenerBlock` на macOS 26.5 возвращает `noErr`, а блок
  продолжает вызываться (проверено ревью на приватном агрегате) — слушатели ставятся
  через `AudioObjectAddPropertyListener` с C-функцией.
- Если у устройства вывода есть входы (AirPods, USB-гарнитура), во входных потоках
  агрегата первым идёт микрофон устройства, а не tap — `TapCapture` ищет поток tap по
  формату и положению.
- Объект процесса Core Audio есть у всех, кто хоть раз трогал звук (Telegram, Safari,
  Chrome, PowerPoint в списке с `output=0`) — tap можно создать до звонка; у только что
  запущенного приложения без звука его нет.

## Решение и следствия для этапа 3

- Канал собеседника — ScreenCaptureKit, фильтр `including: [приложение]`, аудио 16 кГц
  mono прямо из `SCStreamConfiguration` — формат диктовки без ресемплинга; тишина идёт
  непрерывно, дорожка пишется по кадрам без подкладывания по часам.
- Первое согласие: ловить −3801, показывать инструкцию и кнопку перезапуска. Ключей в plist
  «Запись экрана» не требует: сборка 160000 без `NSAudioCaptureUsageDescription` (ключ удалён
  из бандла, переподписано) даёт речь через SCK как раньше.
- Process tap остаётся запасным для явно выбранного PID (код в `probe/TapCapture.swift`);
  в приложение не берётся.
- Смену устройства вывода проверить на этапе 3 при пользователе: после
  `default_output_changed` следить, что кадры идут, иначе перезапускать поток.
- Фильтр строится на `content.displays.first`; с внешним монитором окна приложения звонка
  могут быть на втором дисплее — проверить на этапе 3, что звук по приложению не зависит от
  дисплея (в спайке один экран).
- Предупреждение об эхе на динамиках (FR-12.1) — обязательно; UX-подсказка «наушники».
