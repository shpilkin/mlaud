# S5 — задержка и цена первой карточки: результат

**Дата:** 2026-09-05 · **Вопрос:** OQ-16 — какая модель по умолчанию, если решает задержка
первой карточки после конца фразы собеседника, а не токены в секунду.

**Кандидаты — по решению пользователя в ходе спайка:** только **DeepSeek V4 Flash** и
**GLM-5.3 Flash** (Claude исключён как дорогой, локальный Qwen отложен). Шлюзы — те, что у
пользователя уже есть: RouterAI (подключение из Niti, цены в рублях) и OpenRouter (цены в
долларах, сам считает стоимость).

**Вердикт: DeepSeek V4 Flash через OpenRouter, рассуждения выключены явно, ответ короткий —
первая карточка через 3.4 с (медиана), 3.9 с в худшем из десяти ходов, полный ответ 5.7 с,
около цента за час звонка.** Гейт плана «медиана ≤ 3 с» не взят ни одним кандидатом: лучший
промахивается на 0.4 с и принят по умолчанию, потому что остальные комбинации в 1.5–10 раз
медленнее, а оставшийся рычаг — ещё меньше карточек в ходе (п. 8). Три рычага, без которых
ни одна модель не подходит к коридору: выключить рассуждения, резать длину ответа, отдавать
карточки стримом.

## Как мерили

`run.py openai …` (этот каталог): одна беседа на звонок (feature-prompter.md §7.2) —
системный промт из роли, реального профиля (прототип суфлёра), брифа встречи и материалов
(описание продуктов + расшифровка прошлой встречи), ~30 тыс. токенов по счётчику
DeepSeek (27.6 тыс. GLM, 44–53 тыс. Claude); десять ходов по ~2.5 минуты реплик из реальной
расшифровки (`Запись 14`, «Я» / «Собеседник»); структурированный вывод по схеме карточек
(`response_format: json_schema`); ответ модели остаётся в истории как ход ассистента.

Путь замера — не тот, что был записан в плане: не SDK Anthropic с явными точками кэша, а
OpenAI-совместимый HTTP (`/chat/completions`, SSE) через сторонние шлюзы с автоматическим
кэшем на стороне провайдера; этот же путь идёт в приложение (FR-12.13). Схема в `run.py`
по-прежнему требует поле `detail` (в коротком варианте — пустая строка): контракт
feature-prompter.md §7.3 убрал его уже после спайка, так что команда воспроизведения ниже
повторяет измеренные числа, а не итоговый контракт.

Стрим: засекаем **первый токен** и **первую целую карточку** (закрылся первый объект в
`cards`), помимо полного ответа. Три варианта на модель:

| вариант | что меняется |
|---|---|
| как есть | параметры по умолчанию шлюза |
| без рассуждений | `reasoning: {"enabled": false}` |
| коротко | + `detail` пустой, ≤ 3 карточек, `text` ≤ 100 символов, повестка — только изменения |

`flash-*` — RouterAI, `or-*` — OpenRouter. Пояснения к пустым и неполным строкам:

- **or-ds-asis** упал на 4-м ходу: DeepSeek в режиме рассуждений вернул невалидный JSON
  (запятая перед `}`); три хода до этого — в таблице.
- **or-glm-noreason / or-glm-terse** — OpenRouter отвечает 400 «Reasoning is mandatory for
  this endpoint and cannot be disabled»: у GLM-5.3 Flash на OpenRouter рассуждения не
  выключаются. На RouterAI «выключение» оставляет 16–24 токена рассуждений — и работает.
- **Claude, измерено до отмены** (пользователь снял с кандидатов как дорогих; через RouterAI,
  с точкой кэша на системном сообщении): `claude-opus-5` — 11.5 с медиана, 23.7 макс, ≈ 80 ₽
  ($0.8) за час; `claude-sonnet-5` — 15.5–17 с на трёх ходах, затем крах на «JSON + текст
  после него». Оба в 2–3 раза медленнее DeepSeek без рассуждений при цене в 80 раз выше.
- Первый прогон DeepSeek через RouterAI без стрима (`routerai-deepseek-v4-flash`): 23.5 с
  медиана, кэш срабатывал через раз — RouterAI-бэкенд DeepSeek и медленнее, и с нестабильным
  кэшем.

## Что это значит

1. **Модель по умолчанию — `deepseek/deepseek-v4-flash` через OpenRouter, рассуждения выключены
   явно (`reasoning: {"enabled": false}`).** Единственная комбинация рядом с коридором: 3.4 с при
   гейте ≤ 3 с. Без явного
   выключения DeepSeek рассуждает по 100–1100 токенов на ход и первая карточка уходит за 10–20 с.
2. **Шлюз — часть модели.** Та же модель с теми же параметрами через RouterAI даёт первую
   карточку за 8.8 с против 3.4 с: бэкенд генерирует втрое медленнее (≈ 35 против ≈ 100
   токенов/с), первый токен позже на секунду, кэш промта срабатывает не всегда. Подключение в
   настройках хранит и шлюз, и модель; менять одно без замера другого нельзя.
3. **Длина ответа — второй по силе рычаг.** Короткий формат (без `detail`, ≤ 3 карточек,
   повестка только изменениями) режет вывод с ~600 до ~320 токенов и полный ответ с 7.7 до
   5.7 с. Отсюда изменение контракта (feature-prompter.md §7.3): в живом ходе `detail` не
   возвращается, раскрытие карточки — отдельный запрос по требованию; повестка приходит
   изменениями, а не целиком.
4. **Карточки — стримом.** Первая целая карточка приходит на 2.3 с раньше полного JSON
   (3.4 против 5.7 с). Разбор ответа в `mlaud_worker.prompter` — инкрементальный: карточка
   показывается, как только закрылся её объект; полный JSON проверяется в конце.
5. **GLM-5.3 Flash — запасной вариант, не по умолчанию.** По умолчанию он рассуждает по
   700–3400 токенов на ход; на OpenRouter рассуждения не выключаются совсем, но
   `reasoning.effort: low` в коротком режиме даёт первую карточку за 3.8 с (медиана) — почти
   как DeepSeek, — однако с разбросом до 6.5 с и кэшем промта, который срабатывает через раз
   (в 3 ходах из 10 — 0 токенов из кэша), отчего ход стоит в 2–4 раза дороже. На RouterAI
   кэш нестабилен ещё сильнее (0 из 10 ходов) и худший ход 31.8 с. При этом содержательно
   карточки GLM были заметно точнее: цитировал термины из разговора, ловил
   уход от повестки, тогда как DeepSeek чаще выдавал шаблонное «спроси / предложи».
   Вывод: DeepSeek по умолчанию, GLM с `effort: low` — второе подключение в списке, и цикл
   настройки промта DeepSeek на живых звонках.
6. **Деньги — не ограничение.** Около цента за час звонка у DeepSeek, 2–3 цента у GLM: потолок
   стоимости в настройках может быть щедрым; ограничивать надо задержку, а не расход.
7. **Разбор JSON должен быть терпимым.** DeepSeek с рассуждениями раз в четыре хода вернул
   невалидный JSON, Sonnet через шлюз дописал текст после JSON. Правило: первый объект через
   `raw_decode`, срез ```-ограждений, одна повторная попытка при неудаче, без падения сессии.
8. **Сквозная задержка в приложении будет больше.** К 3.4 с добавляются 0.8 с паузы VAD и
   ~0.2 с разбора фразы (S1): от последнего слова собеседника до первой карточки — около
   4.5 с. Дальше резать можно только ответ: одна-две карточки без повестки в живом ходе.

## Чего замер не покрывает

- Качество карточек мерилось глазами на двух ходах, не по критерию; цикл настройки промта
  — этап 4, на живых звонках.
- Один день, одна сеть, один регион: задержки шлюзов плавают; в приложении нужен показ
  задержки по ходу, а не одна цифра из спайка.
- Кэш промта на OpenRouter/DeepSeek автоматический (28–41 тыс. токенов из кэша на каждом
  ходу) — управлять им нельзя; при смене провайдера внутри OpenRouter может пропасть.

## Воспроизведение

```bash
# ключи — файлами 0600 вне репозитория
poc/prompter-latency/.venv/bin/python poc/prompter-latency/run.py openai \
  --base-url https://openrouter.ai/api/v1 --key-file <openrouter.key> --model deepseek/deepseek-v4-flash \
  --reasoning-json '{"enabled": false}' --terse --stream --label or-ds-terse
poc/prompter-latency/.venv/bin/python poc/prompter-latency/costs.py <routerai.key> <openrouter.key>
```

Матрицы целиком — `flash.sh` (RouterAI) и `openrouter.sh`; сырые ответы и сводки —
`~/ASR/spikes/prompter-latency/`, вне репозитория.
